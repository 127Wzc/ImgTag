# 主体管理、提炼与历史

## 使用流程

1. 管理员在“主体管理”创建或编辑主体；主体关联已有主名称标签，别名也使用普通标签。创建时关联带主名称标签的图片，保留原有其他主体。
2. 点击“提炼”，手选包含主名称标签的参考图。每次最多3张，第一张在成功提交后成为封面；上限可在系统设置中调整为1–3张。补充规则、背景资料和请求预览在“更多设置”中。
3. 点击“提炼并更新”提交后台任务。成功后直接更新主体描述、保留识别备注，失败保留原内容。同一主体同时只允许一个提炼任务；失败后重新选择参考图提交。
4. 需要更新已有图片时，点击“更新描述 · N 张”。范围为当前关联图片，确认数量后入队，分析成功直接生效。

提炼描述只保留身份和识别特征，通常1–3句话；来源、参考图编号和待确认事项放在任务结果中。样本用于本次分析，不训练识别器。

## 历史与权限

每个主体保留最近三份替换前的描述和识别备注，当前资料不占额度。“历史”中可回退或删除指定备份，两种操作均需确认。回退前先备份当前内容；删除不影响当前资料。

主体创建、资料编辑、提炼、样本及历史管理仅管理员可操作。普通用户按原有权限维护自己图片的标签，关联使用已有主体；已有主体关联 API 同样只允许图片所有者或管理员操作，触发重新分析仍需 AI 分析权限。标签修改沿用原有权限，标签改名继续同步主体名称和别名。普通用户不能读取主体定义、识别备注、参考图或登记主体样本。回退有版本校验，提炼期间身份信息变化则拒绝应用旧结果；回退主体资料不会自动改写已有图片。

## 分析如何使用主体

- 调用视觉模型前，程序读取当前主体关联与普通标签，组装主体资料快照；只重建向量或跳过视觉分析时不执行这一流程。无命中时传空资料列表，不将全部主体库交给模型。
- 同一主体的名称和别名归并为一份资料；不同主体按位置区分，同一主体可出现多次。
- 外观、服装、动作、数量和场景以当前图片为准，不把定义中不可见的设定写成事实。明显冲突提示检查，不自动修改人工关联。

### 输入字段与维护入口

以下 key 由程序定义，value 从已保存资料和当前图片关系生成，不由本次视觉模型编造。

| 字段 | 来源与含义 |
| --- | --- |
| `subject_id` | 主体数据库 ID，用于对应资料和模型核实结果 |
| `name`、`aliases` | 主体编辑界面的名称、别名；与主名称及别名标签同步 |
| `definition` | 主体编辑界面的“描述”，对应数据库 `description`；也可由提炼成功后的 `analysis_context` 更新 |
| `recognition_notes` | 后端保留的识别备注，默认空串；当前主体编辑界面没有独立维护入口。日常识别特征、易混淆点统一写入“描述”，提示词不应依赖备注非空 |
| `source` | 当前关联或线索来源，如 `manual`、`approval`、`tag`、`user_tag`、`tag_candidate` |
| `status` | 每次组装时生成的资料可信度：`confirmed` 或 `candidate`，不是主体编辑表单字段 |
| `version`、`definition_revision` | 主体更新时间和定义修订号，用于识别资料变化 |
| `assignment_version` | 已确认关联的更新时间；仅已有已确认关联的资料包含该字段 |

名称和别名用于身份对应，不是视觉证据；描述提供识别背景，当前资产中的可见事实决定外观、动作与场景。分析期间主体资料或关联发生变化时，旧结果会被丢弃并重新排队。

### 输入状态如何产生

输入 `status` 表示程序根据关联和标签给予的信任，不等于已经通过本次视觉识别。

| 当前图片的情况 | 输入状态与处理 |
| --- | --- |
| 已有 `state=confirmed` 的当前关联，且主体启用 | `status=confirmed`，保留关联的 `source` |
| 没有当前关联、没有显式主体选择记录，人工标签仅命中一个主体，且分析流程允许按标签关联 | 自动建立 `source=tag、state=confirmed` 的关联，再以 `status=confirmed` 传入 |
| 未关联主体被人工来源普通标签唯一命中，且无显式主体选择记录 | 可作为 `source=user_tag、status=confirmed` 的资料传入；不代表一定建立了关联记录 |
| AI 标签命中、人工标签存在歧义，或已有显式选择使其他标签命中不能作为可信身份 | 未关联命中主体作为 `source=tag_candidate、status=candidate` 传入 |
| 关联与标签均无命中，自动匹配也无命中 | 传空资料列表 |

“唯一命中”按主体的主名称标签或别名标签判断，不是按画面相似度判断。已关联主体不重复作为标签候选加入。`image_subjects.state` 是保存的关联状态，输入 JSON 的 `status` 是本次资料快照状态，二者不应混为同一字段。

外部上传的 `tags` 保存为 `source=user`，同样参与上述规则。例如新图上传 `tags: ["菲比"]`，在实际进入视觉分析、标签唯一命中已启用的“菲比”主体且满足自动关联条件时，会先建立已确认关联，再向模型提供该主体资料。这不要求此前手动选择过主体，标签填错也可能带入错误身份。

`auto_analyze=false` 不触发上述分析期自动关联；同时提供有效标签和描述、且未提供非空 `analysis_instructions` 时，即使 `auto_analyze=true` 也会跳过视觉分析，因此不能仅凭开关开启判断是否建立了主体关联。

### 模型输出与后台校验

有主体资料时，程序附加输出协议，要求模型生成以下字段；它们不是手动维护的主体资料。

| 输出字段 | 含义 |
| --- | --- |
| `subject_checks` | 每份主体资料一条核实结果：`subject_id`、`status`（`supported` / `uncertain` / `conflict`）和 `evidence`（依据） |
| `subject_observations` | 可见观察：`subject_id`（可为 null）、`position`、`appearance`（不含姓名的可见外观动作）、`multiple`（同一画面是否有多个该主体） |

输出 `status` 与输入 `status` 使用不同取值：前者是本次核实结果，后者是资料可信度。后台拒绝未知主体 ID 和重复核实 ID；缺失核实、或 `supported` 缺少依据时先按 `uncertain` 处理。对于输入已为 `confirmed` 的身份，后台会将 `uncertain` 转为 `supported`，注明采用已确认身份；`conflict` 不会这样转换。因此保存的 `supported` 不一定表示模型独立识别成功。

后台按核实结果规范化身份标签；描述中出现未获支持的已知名称时，使用可见观察降级处理，表情包优先仅替换主体段。字段校验不能证明视觉依据真实，也不能保证位置、数量和身份识别完全准确。GIF 多帧属于同一资产的不同状态，不跨帧累计主体数量。

## 数据与职责

| 模块 | 职责 |
| --- | --- |
| `subjects` | 规范名称、主名称标签、别名标签、描述、识别备注及封面 |
| `image_subjects` | 当前或历史关联、主主体、来源与标签归属 |
| `subject_samples` | 参考图片及标注；当前不写识别向量 |
| `subject_context_service` | 合并人工关联与标签候选，按主体去重 |
| `subject_assignment_service` | 设置关联、同步标签，保护人工结果 |
| `subject_extraction_service` | 多图提炼、直接更新、历史备份与回退 |

标签改名同步规范名称，引用中的分类、主名称及别名标签不能直接删除。切换主体只移除该流程新增且有归属记录的标签，不删除已有人工标签。

## 自动匹配

默认 `subject_matcher_backend=stub`，始终无命中；未接入真实识别器。人工确认优先，自动结果不能覆盖人工或审批确认的身份。

代码预留了自动匹配分支：允许自动应用的高置信结果可建立 `source=auto、state=confirmed` 关联，其余有效命中可作为 `matcher_candidate` 传入。当前占位后端不会产生这些命中，不能将其视为已实现的视觉身份识别能力。

主要配置为 `subject_memory_enabled`、`subject_auto_apply_high_conf`、`subject_high_threshold`、`subject_low_threshold` 和 `subject_max_candidates`；默认值以 `core/config_defaults.py` 为准。

接入真实识别器时，应明确模型与向量维度、按模型隔离样本检索，并通过误报验证调整阈值。自动命中不直接回流为训练样本，避免错误自我强化。

提示词与图片历史见[图片分析](reanalysis.md)，升级步骤见[数据库管理](database.md)。
